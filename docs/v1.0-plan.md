# WebGL Fractal Explorer 1.0 Plan

Status: Planning  
Target release: `v1.0`

## Execution Checklist

- [x] Add formula visibility and one-click copy support to the HUD
- [x] Replace fixed CPU worker override with auto sizing from available logical processors
- [x] Clean up state modeling so tours, compare mode, and expanded sharing have a stable base
- [x] Add guided tours with curated stops and explanatory notes
- [x] Add explanation tooling and inspector surfaces in the HUD
- [x] Add compare mode with synchronized camera controls
- [x] Add browser-native lightweight export
- [x] Add perturbation/reference-orbit deep zoom for an intentionally limited formula set
- [x] Add dedicated developer documentation for the perturbation backend
- [x] Add perturbation health diagnostics to the inspector

## Purpose

This document turns the current product goals into an implementation plan for `v1.0`.
It is intentionally practical: what to build, in what order, what needs architectural work,
what can ship incrementally, and what should count as done.

## Current Baseline

The project already has strong foundations:

- WebGL-first rendering
- CPU refinement via Web Workers
- 65 fractals across multiple categories
- URL sharing
- per-fractal view memory
- minimap and keyboard controls
- triple-single precision on the GPU and double precision on the CPU

The `v1.0` goal is to move from "capable fractal playground" to "distinguished browser-native fractal explorer".

## 1.0 Product Goals

`v1.0` should improve five areas:

1. UI clarity: formula visibility and copyability
2. renderer scaling: worker count based on available processors
3. technical prestige: perturbation/reference-orbit deep zoom
4. exploration depth: compare mode, guided tours, explanation tooling
5. browser-first product quality: stronger sharing, UX polish, lightweight export

## Non-Goals For 1.0

To keep `v1.0` focused, do not treat these as required:

- adding many more fractal families just to increase the count
- building a full custom formula editor/compiler
- introducing a build step unless a major architectural need emerges
- desktop-native export pipelines
- multiplayer or server-backed accounts

## Guiding Principles

- Preserve zero-install browser use.
- Keep the fast GPU preview path responsive at all times.
- Ship new features behind simple, understandable controls.
- Add comments around advanced math and renderer internals so new developers can follow the system.
- Prefer URL-shareable state over opaque local-only state where practical.

## Workstreams

## A. Formula Visibility In The HUD

### Goal

Show the active fractal formula in the control panel and let the user copy it easily.

### Why It Matters

- makes the explorer feel more serious and educational
- reduces the "black box" feeling
- supports explanation tooling later

### Proposed Scope

- add a read-only "Formula" row in the HUD
- show a human-readable formula string for the selected fractal
- add a copy button next to the formula
- support multiline formatting where needed for longer formulas
- include formula text in share/export metadata where reasonable

### Implementation Notes

- add a `formulaDisplay` field to the fractal registry in `fractals.js`
- do not derive display text from raw GLSL shader source
- keep the registry value curated and readable
- where a fractal has special notes, optionally store `formulaNotes`

### Acceptance Criteria

- every fractal shows a formula string in the panel
- the formula text is selectable or copyable with one click
- the layout stays usable on mobile widths

## B. Worker Count Based On Available Processors

### Goal

Scale CPU refinement workers from the user's available logical processors instead of using a fixed override.

### Feasibility

Yes, this is possible in browsers via `navigator.hardwareConcurrency`.

Important caveat:

- browsers expose logical processor count, not true OS thread scheduling details
- the value may be missing or privacy-reduced in some browsers
- it is a hint, not a guarantee

### Proposed Policy

Use:

```text
workerCount = max(1, hardwareConcurrency - 2)
```

Examples:

- `8` logical processors -> `6` workers
- `16` logical processors -> `14` workers

### Recommended Guardrails

- if `navigator.hardwareConcurrency` is unavailable, fall back to a conservative default
- cap workers to a practical max if memory pressure becomes an issue
- separate "auto" worker selection from any future manual override

### Implementation Notes

- replace `CPU_WORKER_COUNT_OVERRIDE` with an auto-detected value
- surface the active worker count in the UI readout or refine tooltip
- store whether the user is on "auto" or manual worker mode if manual control is added later

### Acceptance Criteria

- worker count scales automatically on supported browsers
- fallback behavior is stable when the browser does not expose processor count
- no regression in current refine behavior on lower-core machines

## C. Perturbation / Reference-Orbit Deep Zoom

### Goal

Introduce a real deep-zoom architecture so the explorer can go meaningfully beyond current GPU triple-single and JS-double limits.

### Why This Is A 1.0 Signature Feature

This is the strongest "technical prestige" item on the roadmap.
It changes the project from a polished browser fractal viewer into a serious deep-zoom renderer.

### Scope For 1.0

Ship a first perturbation implementation for a focused set of formulas:

- Mandelbrot
- Burning Ship
- Tricorn / Mandelbar if the math path remains manageable

Do not require all 65 formulas to support perturbation in the initial 1.0 cut.

### High-Level Architecture

1. Detect when camera depth exceeds native precision comfort limits.
2. Choose a reference point near the viewport center.
3. Compute a high-precision reference orbit on the CPU.
4. Send compact perturbation data to workers.
5. Render per-pixel deltas relative to the reference orbit.
6. Fall back to existing paths for unsupported formulas or shallow zooms.

### Key Design Decision

Use a hybrid renderer:

- existing WebGL path remains the default preview path
- perturbation becomes an opt-in deep-zoom backend for supported formulas
- existing CPU refinement remains useful as a fallback and parity path

### Technical Tasks

- add a precision backend abstraction instead of hard-wiring only "GPU preview + CPU refine"
- define a reference-orbit snapshot format
- add high-precision arithmetic for reference calculations
- implement perturbation delta iteration in workers
- add glitch detection / rebase strategy for invalid regions
- add backend selection logic per formula and zoom depth
- add explicit unsupported-mode handling in the UI

### Developer Documentation Requirement

This work must be heavily commented.

Required comment coverage:

- why perturbation is needed
- what the reference orbit represents
- how delta iteration differs from ordinary escape-time iteration
- when rebasing/glitch correction happens
- why certain formulas are supported first and others are not

Add at least one dedicated developer doc later, likely:

- `docs/perturbation-architecture.md`

### Risks

- large implementation complexity jump
- correctness bugs at extreme zoom
- different formulas may require different perturbation handling
- debugging becomes harder without strong instrumentation

### Acceptance Criteria

- supported formulas can zoom substantially deeper than the current implementation
- backend switching is visible and understandable
- when perturbation is not available, the app degrades gracefully instead of failing silently

## D. Compare Mode

### Goal

Let the user compare two synchronized views.

### Why It Matters

Compare mode is a strong product differentiator because it turns passive viewing into structured exploration.

### Recommended 1.0 Scope

Support:

- same formula, different coloring
- same location, different formula
- same formula, different Julia parameter where applicable
- standard mode vs deep-zoom/perturbation mode when helpful for debugging

### UX Options

Preferred initial implementation:

- split-screen compare

Possible later enhancement:

- draggable before/after slider

### Implementation Notes

- reuse one shared navigation model with two render targets
- allow locking and unlocking camera sync
- keep HUD simple: primary panel plus compact compare panel
- avoid doubling every expensive computation unless compare is active

### Acceptance Criteria

- compare view can be toggled on and off cleanly
- both panes stay synchronized when lock is enabled
- users can independently choose formula/palette for each pane

## E. Guided Tours

### Goal

Make exploration less random by giving users curated routes through interesting locations.

### Recommended 1.0 Scope

- built-in tours for selected fractals
- each tour step contains title, coordinates, zoom, and short note
- next/previous/play controls
- smooth animated camera transitions between stops
- URL support for opening a tour at a given stop

### Data Model

Each stop should include:

- fractal id
- center coordinates
- zoom or pixel scale
- iterations
- optional palette / color mode / Julia parameter
- title
- short explanation

### Implementation Notes

- keep tour content in static JSON-like data in the repo
- start with a small curated set of high-quality tours, not quantity
- tours should work without compare mode enabled

### Acceptance Criteria

- tours are discoverable from the main UI
- transitions are smooth and cancelable by user input
- every shipped tour stop has meaningful explanatory text

## F. Explanation Tooling

### Goal

Explain what the user is looking at instead of only showing pixels.

### Recommended 1.0 Scope

- formula explanation panel for the active fractal
- selected-point inspector
- short notes for interesting tour stops
- plain-language descriptions, not just mathematical notation

### Good First Inspector Fields

- fractal name
- formula text
- coordinates under cursor or selected point
- current zoom
- current effective iterations
- escape / basin mode
- Julia parameter when relevant
- backend in use: GPU / CPU refine / perturbation

### Stretch But Valuable

- orbit trace overlay for selected points
- detected root/basin information for supported formulas
- "why this region is interesting" notes in curated locations

### Acceptance Criteria

- users can inspect the current state without opening developer tools
- explanations remain concise and readable
- inspector data stays in sync with compare mode and tours

## G. Browser-First Sharing

### Goal

Make the app easy to share, reopen, demo, and discuss entirely through the browser.

### Recommended 1.0 Scope

- expand URL state coverage to include tours, compare mode, and formula display context where useful
- add a dedicated "Copy link" confirmation flow that is unobtrusive
- add share presets for current view vs full session
- preserve backward compatibility with existing share links where possible

### Implementation Notes

- keep the URL schema compact but readable enough for maintenance
- version the URL state when needed to avoid breaking old links
- avoid storing giant payloads directly in the query string

### Acceptance Criteria

- a shared link recreates the intended user-visible state reliably
- old basic links still open correctly

## H. Polished UX

### Goal

Make the product feel deliberate and finished, especially during more advanced workflows.

### Recommended 1.0 Scope

- stronger HUD layout hierarchy
- better mobile handling for dense controls
- clearer render/backend status messaging
- smoother transitions for tours and compare activation
- more intentional copy and labels
- formula display that feels integrated, not bolted on

### Specific Areas To Revisit

- control density in the current HUD
- readability of mode status
- discoverability of refine/deep-zoom backend behavior
- layout when compare mode is active
- visual handling of long formulas and explanations

### Acceptance Criteria

- advanced features do not make the HUD feel cluttered
- mobile and desktop remain usable without separate codepaths

## I. Lightweight Export

### Goal

Support simple, browser-native output without turning the app into a heavy render farm.

### Recommended 1.0 Scope

- export current viewport as PNG
- optionally include metadata in exported filename or sidecar text
- export compare mode as a combined image if compare is active
- export current tour stop or current share URL alongside the image

### Not Required For 1.0

- full offline video rendering pipeline
- giant batch render queue
- desktop-class EXR workflow

### Acceptance Criteria

- export works without server infrastructure
- exported images match what the user sees closely enough for normal use

## Recommended Release Phases

### Phase 1: Foundation

- formula display in HUD
- auto worker count from `navigator.hardwareConcurrency`
- renderer/backend status cleanup
- URL state groundwork for new features

### Phase 2: Exploration Features

- guided tours
- explanation panel / inspector
- lightweight export

### Phase 3: Major Product Feature

- compare mode
- compare-aware sharing and export

### Phase 4: Prestige Renderer

- perturbation/reference-orbit backend for a small supported formula set
- backend switching and deep-zoom UI messaging
- developer-facing comments and architecture notes

## Recommended Order Inside The Codebase

1. Stabilize state and URL modeling first.
2. Add HUD data surfaces next: formula, backend, inspector hooks.
3. Add tours and compare mode after state handling is clean.
4. Add perturbation only after the renderer boundary is explicit.

This order reduces the chance of rewriting state logic twice.

## Suggested File-Level Impact

  HUD additions, compare layout containers, tour controls, inspector controls
- `styles.css`
  HUD layout updates, compare layout, formula display styling, tour/inspector styling

  architecture notes for perturbation and feature behavior

The file list above is directional only. This plan does not require the exact final file split yet.

## Risks And Dependencies

- perturbation work may dominate the schedule if attempted too early
- compare mode can increase renderer and UI complexity quickly
- share-state growth can become messy without explicit schema discipline
- explanation tooling becomes weak if formula metadata is not curated well

## Definition Of Done For 1.0

`v1.0` is done when:

- formula text is visible and copyable in the panel
- CPU worker count is auto-scaled from available logical processors with sensible fallback
- compare mode is usable and shareable
- guided tours are present and polished
- explanation tooling makes the explorer easier to understand
- browser-native sharing and export are solid
- perturbation deep zoom ships for an intentionally limited but well-documented supported set
- the advanced renderer code includes enough comments for a new developer to follow the architecture
